# JWT 알고리즘 구조와 확장 검토

현재 활성화된 생성·검증 알고리즘은 HS256, ES256이다. 다른 알고리즘은 아래와 같이 추가 가능성을 검토했으며 실제 지원 목록에는 추가하지 않았다.

## 구조

```text
jwter/
  cmd/                      CLI 입력과 출력, 종료 코드
  token/
    token.go                JWT 구조, JSON, 공통 클레임 검증
    algorithms.go           공통 인터페이스와 활성 알고리즘 목록
  algorithm/
    hs256/hs256.go          HMAC secret 처리와 HS256 서명 메서드
    es256/es256.go          P-256 PEM 처리와 ES256 서명 메서드
```

`cmd`는 기존과 같이 `token.Encode`와 `token.Decode`만 호출한다. 알고리즘마다 명령을 추가하거나 cmd 내부에서 분기하지 않는다.

알고리즘 구현은 아래 인터페이스를 만족한다. 인터페이스는 이를 사용하는 token 패키지에 두고, 알고리즘 패키지는 token 패키지를 import하지 않아 순환 의존성을 피한다.

```go
type algorithm interface {
    SigningMethod() jwt.SigningMethod
    UsesSecret() bool
    ParseKey(data []byte, signing bool) (any, error)
}
```

- `SigningMethod`: 이름과 서명·검증 구현을 제공하는 golang-jwt 메서드. 암호 연산을 직접 재구현하지 않는다.
- `UsesSecret`: secret 입력과 PEM 입력 중 필요한 종류를 고른다. 서로 다른 키 입력을 자동으로 대체하지 않는다.
- `ParseKey`: 생성(`signing=true`)에는 서명 키, 검증(`false`)에는 검증 키를 반환한다. 키의 구체적인 타입·곡선·형식 검증은 해당 알고리즘이 담당한다.

입력 크기, 빈 키, secret/PEM 중복은 token 패키지에서 공통 검사한다. ES256의 엄격한 PEM 경계 검사와 P-256 제한은 es256 패키지로 이동했다.

## 등록과 제거

활성 목록은 `token/algorithms.go`의 한 곳에서 관리한다.

```go
var algorithms = []algorithm{
    hs256.Algorithm{},
    es256.Algorithm{},
}
```

추가 절차:

1. `algorithm/<알고리즘명>/`에 위 세 메서드를 구현한다.
2. 해당 알고리즘의 독립된 고정 토큰·키 자료, 생성 결과 검증, 잘못된 키 및 다른 알고리즘 거부 테스트를 추가한다.
3. `token/algorithms.go`에 import와 목록 항목을 추가하고 지원 목록 테스트 및 문서를 갱신한다.
4. 모듈 전체 test/vet/build를 실행한다.

제거할 때는 같은 파일의 목록 항목과 import를 제거한다. 해당 알고리즘의 생성·검증 및 명시적인 `--alg` 사용이 거부되고 도움말에도 나타나지 않는다. 더 이상 사용하지 않는 구현 디렉터리와 관련 테스트·문서도 함께 정리한다.

CLI 도움말과 지원하지 않는 `--alg`의 오류 메시지는 `SupportedAlgorithms()`에서 이름을 가져온다. 반환 목록을 호출자가 수정해도 활성 목록은 바뀌지 않는다. 런타임 플러그인 로딩이나 자동 등록은 사용하지 않는다.

## 선택과 검증 규칙

생성은 명시적인 `--alg`로 목록에서 하나를 선택한다. 검증은 `--alg`가 있으면 이를 사용하고, 없으면 header의 `alg`로 활성 목록에서 하나를 선택한다. 선택한 구현의 입력 종류와 키 타입을 검사한 뒤 원래 compact token 바이트를 검증한다. 여러 알고리즘으로 서명을 차례로 시도하지 않는다.

- 명시한 알고리즘이 비활성/미지원이면 입력 오류(종료 2)다.
- 추정한 알고리즘이 비활성/미지원이거나 입력 종류가 맞지 않으면 검증 실패(종료 1)다.
- 선택한 알고리즘의 키 파싱·형식 검사가 실패하면 입력 오류다. 조회 전용으로 전환하지 않는다.
- 키 없는 조회는 활성 목록 밖의 알고리즘도 읽을 수 있다. 모든 조회 결과에 header, payload, validation을 포함하며 키가 없으면 미검증 상태를 표시한다.
- `verify`는 명시적인 `--alg`와 키를 필수로 받는다. 동일한 파싱·서명 검증 경로를 사용한 뒤 `token/verify.go`의 정책을 검사한다. HS256 최소 32바이트 키 길이 정책과 claim·시간 정책은 `verify`에 적용되며 기존 `decode` 동작은 유지한다.
- 같은 키 종류에 속하는 알고리즘을 추가하더라도 신뢰할 수 있는 기대 알고리즘을 아는 사용자는 `--alg`로 고정할 수 있다.

## 추가 가능성 검토

아래는 현재 고정한 golang-jwt v5.3.1과 표준 키 형식을 기준으로 한 검토다. 라이브러리에 존재한다는 사실만으로 CLI에서 활성화하지 않는다.

| 후보 | 필요한 입력/작업 | 판단 |
| --- | --- | --- |
| HS384, HS512 | raw secret, 각 해시에 맞는 HMAC 메서드와 고정 벡터 | 추가 비용이 작다. 새 의존성 불필요 |
| ES384, ES512 | 각각 P-384, P-521 PEM 키. 해당 곡선·서명 길이 검사 | 기존 ES256 패턴으로 확장 가능 |
| RS256, RS384, RS512 | RSA PEM 개인키/공개키 파싱, 최소 2048-bit 키 제한과 벡터 | 라이브러리에서 지원. RSA 연동이 필요하면 우선 검토할 후보 |
| PS256, PS384, PS512 | RSA 키, PSS salt 길이 정책과 벡터 | 라이브러리에서 지원. 현재 기본 검증 메서드는 salt 길이 자동 수용이므로 허용 정책을 명시해야 함 |
| Ed25519 | PKCS#8 개인키/PKIX 공개키, 명시적인 Ed25519 alg 이름 어댑터와 호환성 테스트 | 확장 가능. v5.3.1 기본 메서드는 `EdDSA` 이름을 사용하므로 그대로 등록하면 새 이름을 지원하지 못함 |
| EdDSA | 라이브러리의 Ed25519 구현을 해당 기존 alg 이름으로 사용 | 호환 목적으로 검토 가능하나 신규 기본 후보로 권장하지 않음 |
| ES256K, Ed448 | 현재 라이브러리 기본 목록 밖의 곡선/서명 구현과 추가 검증 | 요구가 있을 때 별도로 검토 |
| none | 서명 없는 토큰 | 현재처럼 조회만 허용하고 생성·검증은 활성화하지 않음 |

2026-10-21에 확인한 IANA 등록부에서 `EdDSA`는 deprecated이고 `Ed25519`/`Ed448`은 별도 알고리즘으로 등록되어 있다. 이는 Ed25519 서명 자체의 폐기와 구분해야 한다. 새 알고리즘 추가 시 기존 서비스가 사용하는 header 이름과의 호환성도 확인한다.

## 검증 범위

기존 HS256/ES256 공개 벡터, 독립 서명 검증, 잘못된 키·곡선·PEM 거부, 알고리즘 혼동 거부, 숫자 정밀도, 시간 경계, body/상세 출력, 세 입력 방식의 중복 거부 테스트를 유지한다. 새 활성 목록과 CLI 도움말의 연결도 검증한다. 추가 후보들의 실제 서명·검증은 이번 변경의 검증 범위가 아니다.
