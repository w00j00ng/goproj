# tdelta 구현 계획

> 작업 순서와 수용 기준은 7절과 8절을 따른다.

**Goal:** 두 UTF-8 텍스트의 변경을 Git과 유사하게 표시하고, COPY/INSERT delta를 zlib으로 저장하여 정확한 원문 A에서 결과 B를 생성하는 독립 Go CLI를 만든다.

**Architecture:** 작업량을 제한한 행 비교에서 연속 변경 구간을 만들고, 저장용 delta와 화면용 unified diff에 공유한다. delta는 기준 A에서 복사할 바이트 구간과 새 바이트를 단일 zlib 스트림에 저장한다. 편집기는 색상 코드가 없는 임시 `.diff` 문서를 연다.

**Tech Stack:** Go 1.27.4, 기존 도구와 같은 Cobra v1.8.0, `compress/zlib`, `encoding/binary`, `crypto/sha256`, `os/exec`. 행 비교에는 `github.com/hexops/gotextdiff@v1.0.3`의 Myers를 사용한다. Unified diff는 모듈 안에서 작성한다. 터미널 판정에는 기존 도구에서 사용하는 `golang.org/x/term@v0.47.0`을 사용한다. 의존성 추가 시 라이선스·고정 버전·보안 검사와 아래 수용 테스트를 확인한다.

## 1. 확정 범위

프로그램명과 실행 명령은 **tdelta**다. 텍스트의 차이를 표시하고 delta를 저장·적용하는 기능을 표현한다.

2026-11-17 사용자 선택에 따라 **단방향**으로 구현한다.

| 기능 | 초기 지원 |
| --- | --- |
| A와 B의 차이 계산 | 지원 |
| A + 저장된 delta → B | 지원, 공백·개행을 포함한 바이트 단위 일치 |
| B + 같은 delta → A | 제외 |
| Git과 유사한 터미널 unified diff | 지원 |
| 설정된 편집기로 diff 문서 열기 | 지원 |
| A + delta로 diff 다시 보기 | B 생성·검증 후 지원 |
| Git packfile 읽기·쓰기 또는 Git 저장소 필요 | 제외 |
| delta 연결, 여러 버전 저장, 이동 블록 전용 탐색 | 제외 |
| 에디터의 전용 좌우 비교 화면·difftool 등록 | 제외, 초기에는 `.diff` 문서 보기 |
| 에디터에서 수정한 내용을 원문·delta에 반영 | 제외 |

삭제된 원문은 delta에 저장하지 않는다. 화면의 삭제 행은 A에서 가져온다. B만 있으면 이 delta로 A를 복원할 수 없으며, 이것은 지원하지 않는 동작이다. 원문의 해시는 파일 식별·불일치 검사용이고 삭제 내용을 대신하지 않는다.

입력은 UTF-8로 한정한다. BOM, 탭, LF/CRLF, 마지막 개행, 한글 조합 표현은 자동 변환하지 않는다. UTF-8이 아닌 입력과 NUL을 포함하는 입력은 바이너리 입력 오류로 처리한다. 터미널 표시 시 ESC 등 제어 문자는 이스케이프하여 출력하고, 원본 바이트는 저장·적용 과정에서 유지한다.

## 2. CLI 계약

```text
tdelta diff A.txt B.txt
tdelta diff A.txt B.txt --color=never
tdelta diff A.txt B.txt --editor
tdelta diff A.txt B.txt --editor --editor-command "code --wait"

tdelta create A.txt B.txt --output change.dcd
tdelta apply A.txt change.dcd --output B.generated.txt
tdelta apply A.txt change.dcd --output -

tdelta show A.txt change.dcd
tdelta show A.txt change.dcd --editor
```

- `diff`: 파일 경로로 받은 A/B를 비교하여 변경 내용을 표시한다.
- `create`: 압축된 delta 파일을 생성한다. `--output`은 새 파일 경로로 필수 지정하며 stdout 출력은 제공하지 않는다. 화면용 diff를 섞지 않는다.
- `apply`: A와 delta를 검증하여 B를 생성한다. `--output`은 필수이며 `-`는 stdout을 뜻한다.
- `show`: A + delta로 B를 생성·검증하고, A와 B의 unified diff를 표시한다.
- 파일 입력의 `-`는 stdin이다. 하나의 명령에서 stdin을 두 입력에 동시에 지정할 수 없다.
- `diff`와 `show`의 종료 코드는 동일 0, 변경 있음 1, 입력·검증·출력·편집기 오류 2다.
- `create`와 `apply`는 정상 처리 0, 오류 2다. 도움말은 0이다.
- `--editor-command`는 `--editor`와 함께 사용한다. 편집기를 사용한 경우에도 diff/show의 비교 결과 종료 코드를 유지하되, 실행 실패가 있으면 2를 반환한다.
- 초기 입력 상한은 A/B 각각 8 MiB, 압축 파일 16 MiB, 해제된 명령 스트림 32 MiB다. 상한을 CLI 설정으로 노출하지 않고 오류 메시지와 README에 명시한다. 공개 전 성능 검증에서 이 상한의 안전성을 확인한다.
- `--output` 파일은 새 파일만 생성한다. 기존 파일, A/B/delta와 같은 경로, 기존 symlink는 거부한다. 실패 시 기존 파일을 덮어쓰거나 삭제하지 않는다.
- Git 설정 변경, 저장소 초기화, 원문 자동 덮어쓰기, 원격 접근은 수행하지 않는다.

## 3. 저장 형식 v1

확장자는 `.dcd`이며 Git packfile과 호환되지 않는 전용 형식이다. gzip, JSON payload, 사용자 지정 압축 수준, 사전 압축 모드는 추가하지 않는다.

```text
외부 헤더
  magic       : ASCII "TDLT" (4 bytes)
  version     : 0x01 (1 byte)
  base_size   : unsigned varint, A의 바이트 길이
  target_size : unsigned varint, B의 바이트 길이
  base_hash   : SHA-256(A), 원시 32 bytes
  target_hash : SHA-256(B), 원시 32 bytes

본문
  단일 zlib 스트림, DefaultCompression
    0x01 COPY   : offset(uvarint), length(uvarint)
    0x02 INSERT : length(uvarint), 이어지는 length bytes
```

명령은 출력 순서로 기록한다. 끝은 zlib을 정상 EOF까지 읽은 것으로 판정한다. 알 수 없는 opcode·버전, 길이 0의 명령, 잘린 varint·literal, 정수 overflow, 기준 범위 초과, 출력 길이 초과, 체크섬 오류, 스트림 뒤 추가 데이터는 모두 오류다. 빈 B는 명령이 없는 정상 zlib 스트림으로 표현한다.

압축 데이터를 읽는 하위 reader는 `io.ByteReader`도 제공하여 압축기 read-ahead로 추가 데이터를 놓치지 않도록 한다. zlib reader의 `Close`만으로 성공을 판정하지 않고 EOF와 오류를 확인한다. writer의 Write 및 Close 오류를 모두 전달한다.

연속 COPY는 A에서도 연속된 구간일 때 병합한다. 연속 INSERT는 합친다. delta에 사용하지 않은 A의 구간은 저장하지 않는다. 압축 후 크기가 원문보다 작다는 보장은 하지 않으며 v1에는 raw/gzip fallback을 넣지 않는다.

생성한 명령 스트림이 B 전체를 단일 INSERT로 표현한 것보다 길면 단일 INSERT를 사용한다. 두 zlib 결과의 최솟값을 찾기 위한 중복 압축은 하지 않는다. Create도 압축/해제 크기 상한을 지키며, 상한에 맞지 않는 결과를 정상 파일로 반환하지 않는다.

## 4. 변경 계산과 적용

delta 패키지의 호출 계약은 다음과 같다.

```go
package delta

func Create(base, target []byte) ([]byte, error)
func Apply(base, encoded []byte) ([]byte, error)
```

### 비교 작업량 한도

입력 크기와 UTF-8·NUL 조건을 먼저 확인한다. 바이트가 같으면 비교를 생략한다. 다르면 앞뒤에서 일치하는 완전한 행을 제외하고 남은 구간만 비교한다. 행 경계는 `\n`으로 정하고 구분자를 보존한다. 마지막 줄에 개행이 없으면 한 행으로 센다. 행을 세거나 앞뒤를 잘라낼 때 파일 전체의 행 배열을 만들지 않는다. 남은 구간의 한쪽이 비어 있으면 단일 삽입 또는 삭제 구간으로 처리한다.

양쪽에 행이 남으면 합계 `S`가 **1,000행 이하**일 때만 `myers.ComputeEdits`를 호출한다. 고정 버전의 작업 배열 길이는 `2*S+1`이고 편집 거리 단계마다 배열을 보관한다. 64비트에서 `S=1,000`의 최대 배열 사용량은 작업 배열을 포함해 약 15.3 MiB다. 이는 배열 추산치이며 전체 프로세스 메모리 한도가 아니다. 4,096행씩 모두 다르면 trace 배열만 계산상 1 GiB를 넘는다. 파일 크기 상한과 비교 한도는 각각 적용한다.

한도를 넘으면 명령별로 아래 결과를 반환한다. 바이트 크기나 텍스트 형식이 잘못된 입력은 비교 한도와 관계없이 오류다.

| 명령 | 비교 한도 초과 시 동작 |
| --- | --- |
| `create` | B 전체를 단일 `INSERT`로 zlib 압축해 저장하고 0을 반환 |
| `apply` | Myers를 호출하지 않고 기준 A와 결과 B 검증을 통과하면 B를 출력하고 0을 반환 |
| `diff`, `show` | stderr에 남은 행 수와 한도 1,000행을 표시하고 2를 반환. stdout은 비어 있고 편집기는 실행하지 않음 |

### 행 편집을 바이트 치환으로 변환

`myers.ComputeEdits`의 행 좌표는 잘라낸 A 구간 기준이다. 1부터 시작하는 행 번호를 그 구간의 바이트 오프셋으로 변환한 뒤 앞에서 잘라낸 바이트 길이를 더한다. 마지막 행 다음 위치는 정확히 구간의 끝이다. 열 번호 1, 범위, 순서를 검증하고 오프셋이 없는 점에 `Offset()`을 직접 호출하지 않는다.

공통 행이 끼지 않는 연속 편집은 한 치환으로 병합한다. 각 편집의 시작이 직전 편집의 끝과 같으면 A 범위를 이어 붙이고 삽입 바이트는 원래 순서대로 합친다. 예를 들어 `abcdefgh\n` → `abcdEfgh\n`의 삭제 `[0,9)`와 삽입 `[9,9)`을 먼저 `[0,9)` → `abcdEfgh\n`으로 합친다. 렌더러에는 이 행 단위 치환을 전달한다. delta 생성 시에만 병합한 구간의 공통 바이트 접두·접미를 계산하고 두 구간이 서로 겹치지 않게 제한한다.

```text
cursor = 0
각 편집 구간 [start, end), newText를 순서대로 처리:
  cursor부터 start 전까지 COPY
  삭제 구간과 newText의 공통 바이트 접두·접미를 COPY로 보존
  남은 newText를 INSERT
  삭제된 가운데 부분은 저장하지 않음
  cursor = end
원문에 남은 꼬리를 COPY
인접 연산 병합 → 바이너리 인코딩 → zlib 압축
```

행 기반 변경에서도 긴 한 줄의 일부 수정이 전체 행 INSERT가 되는 것을 줄이기 위해 편집 구간의 공통 바이트 접두·접미를 재사용한다. 임의 위치의 동일 블록을 새로 검색하거나 Git의 delta 탐색 알고리즘을 재구현하지 않는다. COPY 위치는 바이트 단위이며 각 명령이 독립된 UTF-8 문자열일 필요는 없고 완성된 결과가 정확해야 한다.

`Apply`는 기준 A가 유효한 UTF-8이고 NUL이 없는지 확인한다. 입력 제한과 헤더를 확인하고 A의 길이·해시가 일치한 뒤 결과 버퍼를 target_size만큼 한 번 확보한다. 명령마다 원문의 slice 또는 INSERT payload를 결과 버퍼에 순차 기록한다. 압축 EOF와 최종 길이·SHA-256을 확인하고, 완성된 B도 유효한 UTF-8이며 NUL이 없을 때만 결과를 반환한다. 명령마다 UTF-8을 검사하면 문자 중간을 나눈 유효한 COPY/INSERT가 거부될 수 있으므로 완성된 바이트열에 적용한다.

정수 검사는 int 변환 전에 수행한다. `offset + length`의 overflow를 피하기 위해 `offset <= base_size`, `length <= base_size - offset`으로 검사한다. 헤더를 믿고 상한을 넘는 메모리를 할당하지 않는다. 임의 delta를 라이브러리의 `ApplyEdits`에 전달하지 않는다.

초기 버전은 입력과 검증된 결과를 메모리에 둔다. 시간은 적용 시 O(|A| + |B| + 해제된 명령 크기)이고, 메모리에는 A·압축 delta·B와 고정 압축 버퍼가 필요하다. 최초 diff 계산의 시간·메모리는 별도이며 이 복잡도 주장에 포함하지 않는다. 대용량 파일을 위한 완전한 스트리밍 API는 추가하지 않는다.

파일 출력은 모든 검증 후 대상 디렉터리 안의 임시 파일에 제한 권한으로 기록하고 닫는다. 완성된 파일을 하드 링크로 공개하면, 같은 경로에 이미 존재하는 파일을 덮어쓰거나 실패 처리에서 삭제하지 않는다. 출력 파일시스템이 하드 링크를 지원해야 한다. stdout에는 검증 완료 전 바이트를 보내지 않는다. 파이프가 닫히는 등 stdout 쓰기가 실패하면 종료 코드 2를 반환하며, 이미 전달된 바이트는 되돌릴 수 없다고 문서화한다.

## 5. 터미널 출력과 편집기

unified 출력은 `--- A`, `+++ B`, `@@ ... @@`, 삭제 `-`, 추가 `+`, 기본 주변 문맥 3행으로 제공한다. Git과 유사한 표시를 목표로 하며 Git의 hunk 선택과 바이트 단위 동일 출력을 약속하지 않는다. 마지막 개행 없음은 표시하고 CRLF 차이·UTF-8 경계·빈 파일을 테스트한다. 렌더링이 내부 비교 바이트를 변경하지 않게 한다.

v1.0.3의 `ToUnified`와 `Unified.Format`은 사용하지 않는다. 모듈의 렌더러는 공통 행에서 A/B 행 위치를 모두 전진시키고, 삭제에서 A만, 삽입에서 B만 전진시킨다. 앞뒤 문맥 3행이 겹치거나 맞닿는 변경 구간은 한 hunk로 묶는다. 문맥을 포함한 각 hunk의 시작을 A/B에서 별도로 저장하고, 각 범위의 행 수는 `공통 + 삭제`와 `공통 + 추가`로 계산한다. 시작이 0부터 센 행 인덱스 `i`일 때 0행 범위는 `i,0`, 1행 범위는 `i+1`, 2행 이상은 `i+1,count`로 표시한다. 잘라낸 공통 앞부분의 행 수도 위치에 포함한다.

`--color=auto|always|never`를 지원한다. auto는 stdout이 지원되는 터미널일 때만 켜고 `NO_COLOR` 또는 `TERM=dumb`이면 끈다. auto의 리다이렉션은 무색이며 always는 stdout에 색상을 강제한다. 편집기 파일은 이 옵션에 관계없이 항상 무색이다. Windows에서 VT 지원을 확인하지 못하면 auto는 무색으로 출력하고, 실제 콘솔 검증을 완료하기 전 지원 완료로 기록하지 않는다. pager는 초기 구현에 추가하지 않는다.

편집기 선택 순서는 다음과 같다.

```text
--editor-command
→ TDELTA_EDITOR
→ VISUAL
→ EDITOR
→ 설정 없음 오류
```

설정은 사용자가 지정한 실행 명령과 옵션으로 구성한다. 인용 부호는 플랫폼 셸에 전달한다. POSIX에서는 `sh -c`의 위치 인자로 임시 파일의 절대 경로를 넘기고 명령 끝에서 `"$1"`로 참조한다. Windows에서는 `exec.Cmd.Dir`에 임시 디렉터리의 절대 경로를 지정하고, 명령 끝에 고정 파일명 `change.diff`를 인자 하나로 붙인다. `cmd.exe /d /v:off /s /c` 호출은 `SysProcAttr.CmdLine`으로 명시한다. Windows에서 설정에 실행 파일이나 옵션의 파일 경로를 직접 적는다면 절대 경로를 사용한다. 이 경우 편집기 프로세스의 기준 디렉터리는 임시 디렉터리다.

`os.MkdirTemp`로 전용 디렉터리를 만들고 그 안에 `change.diff`를 `O_EXCL`과 0600으로 생성한다. Windows는 기본 임시 경로의 사용자 ACL을 따른다. 편집기에 전달하는 파일은 생성한 diff 문서다. stdin/stdout/stderr를 편집기에 연결하여 터미널 편집기도 동작하게 한다.

프로세스가 파일을 사용하는 동안 기다린 뒤 성공·실패 모두 정리한다. GUI는 `code --wait`처럼 파일 닫힘까지 대기하는 명령으로 설정해야 한다. 대기 없이 분리 실행하는 editor는 지원 계약에서 제외한다. 편집기에서 수정한 문서는 원문과 delta에 반영하지 않는다. 동일한 파일은 편집기를 열지 않고 동일하다는 상태만 알린다.

## 6. 파일별 변경 범위

아래 경로는 `goproj` 리포지토리 루트 기준이다. 기존 도구의 helper를 가져오거나 공용 라이브러리를 만들지 않는다.

| --- | --- |
| `tdelta/go.mod`, `tdelta/go.sum` | 독립 모듈과 의존성 고정 |

| `tdelta/internal/delta/delta.go`, `delta_test.go` | 변경 구간의 COPY/INSERT 변환, 바이너리/zlib 인코딩, 검증·적용 |
| `tdelta/internal/delta/benchmark_test.go`, `fuzz_test.go` | 실제 입력 기반 성능 기록·손상 입력 검사 |

공통 설정 변경은 현재 실행 범위에서 제외한다. 향후 CI 등록 시에는 `.github/workflows/security.yml:74`의 `security:scan-batch MODULES`에 `tdelta`를 추가하는 정확한 변경을 제시하고 사용자 승인을 받은 뒤 적용한다. 기존 7개 모듈과 4개 네이티브 실행 환경에 더해 신규 모듈의 검사도 수행하게 되는 영향이다. `Taskfile.yml`과 `tasks` 서브모듈은 변경하지 않는다.

기존 `README.md`는 도구 목록·설치·모듈별 검증 설명에 tdelta를 추가한다. 보안 검사 대상 수는 CI 등록이 승인되어 실제 반영된 뒤에만 8개 모듈·32개 조합으로 수정한다. 공통 실행 설정 승인을 문서 작성이나 일반 구현 요청으로 갈음하지 않는다.

## 7. 작업 순서와 수용 테스트

모든 테스트는 요청값과 기대값을 먼저 나열하고 실제 공개 동작 함수를 호출하여 검증한다. 압축된 바이트열의 완전 일치는 Go 버전 간 계약으로 삼지 않는다. `Apply(A, Create(A,B))`만 확인하지 않고 독립된 기대 결과·수동 구성한 정상 및 손상 파일로 디코더도 검사한다.

### 착수 시 먼저 고정할 회귀 테스트

| 검토 지적 | 입력과 호출 | 기대 결과 |
| --- | --- | --- |
| 1. Myers 메모리 | 서로 겹치지 않는 짧은 행 `a\n` 500개와 `b\n` 500개 또는 501개 | 합계 1,000행은 비교 가능. 1,001행은 Myers 호출 전에 차단. `create`는 단일 `INSERT`, `apply`는 B와 바이트 일치, `diff`·`show`는 2 |
| 2. 행 좌표와 병합 | `abcdefgh\n` → `abcdEfgh\n` 및 1 MiB 한 줄의 중앙 1바이트 치환을 `create`·`apply` | 첫 사례의 명령은 `COPY(0,4)`, `INSERT("E")`, `COPY(5,4)`. 두 사례 모두 복원한 B가 바이트 단위로 일치하고 양쪽 공통 구간을 COPY |
| 3. Hunk 좌표 | 20행 중 2·4·15행 치환, 빈 파일에 한 행 삽입, 한 행을 전부 삭제한 입력을 `diff` | 각각 두 번째 hunk `@@ -12,7 +12,7 @@`, `@@ -0,0 +1 @@`, `@@ -1 +0,0 @@` |
| 4. NUL 거부 | 정상 길이·SHA-256·zlib 체크섬을 가진 delta와 A로 `apply`·`show --editor`. A 또는 복원된 B에 NUL 포함 | 2 반환, stdout 없음, 새 출력 파일 없음, 편집기 미실행 |
| 5. Windows 편집기 | 특수문자가 포함된 임시 디렉터리에서 `.cmd` 대역으로 `diff --editor` | 대역이 `--wait`와 `change.diff`를 각각 한 인자로 받고 올바른 diff를 열며, 프로세스 종료 뒤 파일 정리 |

### 작업 1. 모듈과 사용자 계약

- [ ] `fix/tdelta`에서 독립 모듈을 만들고 기존 작업 상태를 보존한다. 구현 시작 시 별도 변경이 있으면 격리 작업 경로를 사용한다.
- [ ] 위 API와 CLI 인수·종료 코드 테스트를 먼저 작성한다. 없는 API/명령 때문에 실패하는 것을 확인한다.
- [ ] main/Cobra 진입점과 제한된 파일 입력을 구현한다. `cmd.Run(args, stdin, stdout, stderr) int`를 테스트 진입점으로 사용한다.
- [ ] 의존성을 정확한 버전으로 고정하고 라이선스를 확인한다. 버전 교체나 새 공용 helper 없이 수용 테스트를 진행한다.

### 작업 2. 비교 한도, 편집 병합, 단방향 delta

- [ ] 비교 한도와 행 오프셋 테스트를 먼저 작성하고 실패를 확인한다. 경계 입력 외에 앞뒤 공통 행을 포함하면 1,000행을 넘지만 변경은 한 행인 입력, 처음·끝 삽입, 같은 위치의 삽입 순서, 마지막 개행이 없는 EOF, 한글 행을 넣는다.
- [ ] 비교 함수에 사전 한도 검사와 편집 병합을 구현한다. 한도 초과는 고유한 오류로 반환하고 호출부에서 명령별로 처리한다.
- [ ] 아래 입력/기대값 표와 NUL fixture를 `delta_test.go`에 작성하고 실패를 확인한다. NUL 및 잘못된 UTF-8은 zlib이나 해시 손상이 없는 별도 fixture로 확인한다.
- [ ] 바이너리 헤더/명령, zlib 읽기·쓰기와 길이·해시·텍스트 검증을 구현한다. 압축 해제된 명령을 읽어 한 줄 치환의 COPY 사용과 한도 초과의 단일 INSERT를 확인한다.
- [ ] 모든 행에서 Create → Apply 결과가 표의 B와 바이트 단위로 일치함을 검사한다. delta에 원문의 삭제 구간이 없어도 적용되는 손수 작성한 fixture를 별도로 검사한다.
- [ ] 잘못된 A, 손상 파일, 상한 초과에서 결과가 반환되지 않음을 검사한다.

| A | B | 기대 |
| --- | --- | --- |
| 빈 문자열 | 빈 문자열 | 빈 B, 정상 처리 |
| `same` | `same` | B가 동일 |
| 빈 문자열 | `가나다🙂` | 삽입된 B와 정확히 일치 |
| `remove all` | 빈 문자열 | 빈 B, 삭제 원문 보관 없음 |
| `hello cat` | `hello dog` | `hello dog` |
| `a\r\nb\r\n` | `a\nb\n` | LF로 된 B와 정확히 일치 |
| `a\n` | `a` | 마지막 개행 없음 유지 |
| UTF-8 BOM이 있는 A | BOM이 없는 B | B의 BOM 유무 그대로 |
| 반복 구간과 여러 변경점 | 중간 삽입·삭제가 있는 B | 모든 구간과 순서 보존 |
| 1 MiB의 한 줄에서 가운데 일부 교체 | 교체한 B | B 일치, 공통 접두·접미 재사용 |

사용자 관점의 기본 테스트는 다음 형태로 작성한다.

```go
package delta_test

import (
    "bytes"
    "testing"

    "github.com/w00j00ng/goproj/tdelta/internal/delta"
)

func TestCreateApply(t *testing.T) {
    cases := []struct{ name, a, b string }{
        {"empty", "", ""},
        {"same", "same", "same"},
        {"insert", "", "가나다🙂"},
        {"delete", "remove all", ""},
        {"replace", "hello cat", "hello dog"},
        {"newlines", "a\r\nb\r\n", "a\nb\n"},
        {"no final newline", "a\n", "a"},
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            encoded, err := delta.Create([]byte(tc.a), []byte(tc.b))
            if err != nil { t.Fatal(err) }
            got, err := delta.Apply([]byte(tc.a), encoded)
            if err != nil { t.Fatal(err) }
            if !bytes.Equal(got, []byte(tc.b)) {
                t.Fatalf("result=%q; want %q", got, tc.b)
            }
        })
    }
}
```

### 작업 3. 터미널 unified diff

- [ ] 같은 문자열, 한 행 치환, 떨어진 두 변경, 빈 파일, CRLF와 마지막 개행 없음의 기대 출력을 정의한다. 20행 중 2·4·15행만 치환하면 두 번째 헤더는 `@@ -12,7 +12,7 @@`다. 빈 파일에 한 행 추가는 `@@ -0,0 +1 @@`, 한 행을 모두 삭제하면 `@@ -1 +0,0 @@`다. 첫 hunk에서 추가·삭제 수가 다를 때 다음 hunk의 B 위치가 누적 차이를 반영하는 사례도 넣는다.
- [ ] 같은 변경 계산 함수로 unified 출력과 delta를 만들고, 렌더링 과정에서 입력 바이트가 바뀌지 않음을 확인한다.
- [ ] 출력 라벨은 실제 파일 이름을 안전하게 표시하고 stdin에는 명확한 A/B 라벨을 쓴다. stdout writer 오류를 그대로 전달한다.
- [ ] auto/always/never, NO_COLOR, 파일 리다이렉션, 제어 문자 입력에 대해 기대 출력과 색상 유무를 검사한다.
- [ ] `tdelta show A delta`와 `tdelta diff A B`가 같은 비교를 표시하고 0/1/2 계약을 지키는지 검사한다.
- [ ] Myers 한도를 넘는 A/B 및 같은 A와 그 delta를 각각 `diff`와 `show`에 넣고, 종료 코드 2와 빈 stdout을 검사한다. `--editor`를 지정해도 편집기 호출이 없어야 한다.

### 작업 4. 설정된 editor로 보기

- [ ] 설정 우선순위, 미설정, 실행 실패, 비정상 종료를 표 기반 테스트로 작성한다.
- [ ] Windows 실행기 작성 전에 `.cmd` 대역이 `%*`를 Go 테스트 실행 파일로 전달하는 테스트를 준비한다. 공백·한글·`&`·`%TDELTA_TEST%`·`!`를 포함한 임시 디렉터리를 작업 디렉터리로 지정한다. 수신 인자가 `--wait`, `change.diff` 두 개이며 두 번째 인자로 실제 파일을 정확히 열 수 있어야 한다. 테스트는 `code.cmd`의 전달 형태를 검증하고 실제 VS Code 동작은 별도 확인한다.
- [ ] 실제 별도 테스트 프로세스를 editor 대역으로 실행하여 인자, 파일 존재, 파일 내용, 종료 전 보존·종료 후 정리를 검사한다. POSIX에서도 특수문자가 포함된 절대 경로가 인자 하나로 전달되는지 검사한다.
- [ ] 편집기 대역이 파일을 수정해도 A/B/delta가 변경되지 않음을 검사한다. 임시 파일 생성·쓰기·삭제 오류는 성공으로 처리하지 않는다.
- [ ] Windows와 POSIX 호출 경로를 각각 실제 환경에서 검증한다. VS Code `code --wait`와 사용 가능한 터미널 editor로 실제 열기·닫기·정리를 확인한다.

### 작업 5. CLI 통합·실패 경로

- [ ] 실제 CLI를 빌드하여 create → apply → 파일 바이트 비교와 create → show를 실행한다.
- [ ] 동일 결과 0, 변경 1, 잘못된 원문·인수·편집기·출력 2를 stdout/stderr와 함께 검사한다.
- [ ] 기존 출력 파일·입력과 같은 출력 경로·symlink·쓰기 실패에서 기존 데이터가 보존되는지 검사한다.

### 작업 6. 성능·문서·통합 준비

- [ ] 1 KiB, 64 KiB, 1 MiB, 8 MiB에서 동일·소량 수정·대량 삭제·전체 교체·반복 행·한 줄 입력을 측정한다. 생성/적용 시간을 따로 기록한다. 한도 안에서도 긴 바이트 접두부가 반복되는 서로 다른 행을 포함해 비교 비용을 확인한다.

- [ ] 입력 상한에서 최악 사례의 시간·메모리를 확인한다. 완료되지 않거나 과도한 자원을 요구하면 해당 상한의 지원을 선언하지 않고 원인과 필요한 범위 조정을 보고한다.
- [ ] 모듈 README에 단방향 계약, 저장 형식 버전, 종료 코드, editor 설정·대기 조건, 입력 제한, 검증된 운영체제를 기록한다. 루트 README의 도구 목록·설치·검증 설명도 갱신하되 보안 검사 대상 수는 실제 CI 등록 상태와 일치시킨다.
- [ ] 비교 한도 내 최악 사례와 한도 초과 시의 `create` 경로를 별도로 측정한다. 파일 크기 상한 검증에는 `apply`도 포함한다.
- [ ] 아래 검증을 수행하고 결과를 확인한다. 공통 CI 등록은 정확한 변경 승인 후 수행하며 승인 전에는 기존 명령을 우회하거나 workflow를 수정하지 않는다.

## 8. 검증 명령과 완료 조건

리포지토리의 `tdelta/` 모듈 디렉터리에서 실행한다.

```powershell
rtk go test -mod=readonly -count=1 -timeout=2m ./...
rtk go vet -mod=readonly ./...
rtk go build -mod=readonly -o "$env:TEMP/tdelta-check.exe" .
rtk go test -mod=readonly -run '^$' -bench . -benchmem -count=3 ./internal/delta
rtk go test -mod=readonly -run '^$' -fuzz '^FuzzApply$' -fuzztime=30s ./internal/delta
rtk go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...
```

기대 결과는 테스트·vet·빌드 성공, fuzz panic 없음, 도달 가능한 알려진 취약점 없음이다. 벤치마크는 수치와 환경을 기록하며 임의의 압축률·시간을 성공 기준으로 꾸미지 않는다. 별도 네이티브 Linux/macOS 환경에서는 그 플랫폼의 임시 실행 파일 경로로 빌드하고 CLI/editor 시나리오를 실행한다. cross-build만으로 실행 검증을 대체하지 않는다.

완료 조건은 위 다섯 회귀 테스트 통과, 단방향 바이트 일치, 손상 입력의 실패 보장, 0/1/2 종료 코드, 편집기 대기·정리, 기존 데이터 보존과 지원 플랫폼별 실제 검증 기록이다.
